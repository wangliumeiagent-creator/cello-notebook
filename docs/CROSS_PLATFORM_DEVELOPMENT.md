# 网页版与小程序协同开发规范

生效日期：2026-11-05。适用于 `cello-notebook` 与 `cello-miniprogram`。两端保留独立仓库、运行环境、版本和发布流程。

## 每次修改前必须完成双端影响评估

修改曲目或通用功能时，先读取两端最新代码、检查未提交改动与来源提交，填写以下记录后再实施。不得因为当前只打开一个仓库而漏掉另一端；也不要求所有平台界面完全一致。

| 变更类型 | 默认评估与处理 |
| --- | --- |
| 音符、音高、时值、调性、指法、说明、反复与曲目增删 | 默认两端同步；若另一端已经一致，记录无需改动的证据。保留稳定曲目ID、弱起、伸张与换把说明。 |
| 节奏、音高计算、判题、提示计分、记录合并等通用逻辑 | 两端分别检查同一输入的结果，修复共享缺陷；适配代码可以不同，不整文件覆盖。 |
| 交互规则与文案 | 评估两端是否解决同一个用户问题；选择两端同步或单端适配并说明理由。 |
| 微信导航、安全区、触点、权限、浏览器兼容 | 通常只改对应平台；仍须记录另一端评估结论。 |
| 打印、导出、网页部署等已确认平台专属功能 | 只维护拥有此功能的一端，不把网页导出等重新加入小程序。 |
| 开发规范与共享数据约定 | 两仓库的AGENTS和开发文档都应可发现本规范，规则正文同步维护。 |

评估记录最少包含：需求、两仓库来源提交、涉及文件/功能、网页版结论、小程序结论、验证方法、未同步原因、提交及发布状态。结论必须明确为“同步修改”“现已一致无需修改”或“平台专属无需同步”；不能只写“已考虑”。

## 曲库维护

当前曲谱原始录入来源为网页版 `src/library.js`、`laputa.js`、`advanced.js`、`scars.js`、`c-major.js`。小程序 `miniprogram/utils/library.js` 为生成数据，禁止长期手工维护第二套音符。

在小程序仓库使用：

```sh
node scripts/sync-library.cjs --source /本机/cello-notebook --write
node scripts/sync-library.cjs --source /本机/cello-notebook --check
```

同步脚本校验小节、音高和播放路线，记录来源提交与内容摘要，检查时不改文件。若曲目修改先发生在小程序，先将录入更正回来源模块，再生成两端产物；来源已改但尚未提交时不得生成声称可追溯到已提交版本的产物。

练习曲库与游戏可用曲目分开：所有已录入谱子可供看谱练习；游戏只能列出其当前指板能覆盖全部音高的谱子。不得为兼容游戏而删改原谱或把高把位曲目统一标成第一把位。

## 实施与验证

- 保留双方改动，正常合并，不使用强制推送、清理工作区或整目录覆盖解决冲突。
- 曲目改动逐小节校验拍数，并验证弱起、三连音、延音、连弓、一二房、临时记号及小节标签。
- 网页运行测试和构建；小程序运行测试、静态检查及开发者工具验证。通用逻辑以相同输入/边界预期分别验证。
- Web Audio 与微信音频生命周期、DOM 与原生Canvas分别适配；不能用一端通过代替另一端。
- 原网页现有打印/PDF产物按其发布流程维护；小程序不新增打印、导出、权限或联网能力。
- 新曲目与长曲分别检查展示和播放，不以“目录已出现”代表可完整练习。

## 交付与发布

两端分别提交、分别记录版本和变更日志；交付时说明两端哪些改了、哪些无需改及证据。源码推送、网页部署、微信上传、提审和正式发布是独立动作，不相互视为已完成。本规范不自动授权部署网站或发布小程序。
